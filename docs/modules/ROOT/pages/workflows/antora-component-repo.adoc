= Репозиторий компонента с документацией на Antora
:navtitle: Компонент с документацией на Antora

== Цель

Описать контракт репозитория компонента, который хранит AsciiDoc-документацию и подключается к центральной сборке сайта через Antora playbook.

Репозиторий компонента отвечает за собственные страницы, навигацию и правила Cursor.
Центральный репозиторий отвечает за playbook, контейнерную сборку, публикацию и общую структуру сайта.

== Роли репозиториев

[cols="1,1,2", options="header"]
|===
| Роль
| Пример
| Ответственность

| Шаблон компонента
| `cursor-starter-kit`
| Каркас `.cursor/rules`, Antora-компонент в `docs/`, bootstrap-скрипты и процессы создания новых компонентов.

| Центральная сборка
| `shgd_antora_spec_root`
| `antora-playbook.yml`, Docker/Compose, платформенная документация и результат сборки `build/site`.

| Репозиторий компонента
| `antora-test-comp-b`
| Документация одного продукта или подсистемы. Регистрируется в playbook как Git-источник.
|===

== Обязательная структура

Для проектов из этого шаблона используйте структуру с `docs/antora.yml` и подключением через `start_path: docs`.

[source,text]
----
.
|-- README.adoc
|-- LICENSE
|-- .cursor/
|   `-- rules/
|-- docs/
|   |-- antora.yml
|   `-- modules/
|       `-- ROOT/
|           |-- nav.adoc
|           `-- pages/
|               |-- index.adoc
|               |-- templates/
|               `-- ...
`-- scripts/
----

Не размещайте `antora.yml` в корне для проектов из `cursor-starter-kit`.
Корневой вариант подходит только для простых репозиториев документации без `.cursor/` и без дополнительной структуры в `docs/`.

== Контракт `docs/antora.yml`

Минимальный дескриптор:

[source,yaml]
----
name: project-name
title: Название проекта
version: true
nav:
  - modules/ROOT/nav.adoc
----

Правила:

* `name` должен быть уникальным среди всех компонентов центрального playbook;
* `name` используется в межкомпонентных ссылках вида `xref:project-name::page.adoc[]`;
* изменение `name` считается контрактным изменением, потому что ломает внешние `xref`;
* `title` должен быть понятным пользователю сайта;
* `nav` должен ссылаться на существующий `modules/ROOT/nav.adoc`.

== Навигация

`docs/modules/ROOT/nav.adoc` — единственный источник навигации компонента.
При добавлении новой пользовательской страницы обновляйте `nav.adoc`.

Пример:

[source,asciidoc]
----
* xref:index.adoc[]
* Архитектура
** xref:architecture/overview.adoc[]
* Процессы
** xref:workflows/antora-component-repo.adoc[]
----

== Ссылки и include

Используйте Antora-ссылки вместо относительных Markdown-ссылок.

[cols="1,2", options="header"]
|===
| Сценарий
| Синтаксис

| Страница в том же ROOT-модуле
| `xref:architecture/overview.adoc[]`

| Страница в другом модуле того же компонента
| `xref:ROOT:index.adoc[]`

| Страница другого компонента
| `xref:component-name::index.adoc[]`

| Страница конкретной версии другого компонента
| `xref:1.0@component-name::index.adoc[]`

| Вставка локального файла
| `include::example.puml[]`
|===

Файл, указанный в `include::`, должен существовать в репозитории.
Не оставляйте ссылки на будущие файлы без явного решения и проверки сборки.

== Жизненный цикл компонента

=== 1. Создать репозиторий

Создайте пустой GitLab-проект и выполните bootstrap из `cursor-starter-kit`.

Скрипт переносит:

* `.cursor/rules/`;
* `docs/antora.yml`;
* `docs/modules/`;
* `README.adoc`;
* `.gitignore`, если он есть в шаблоне.

=== 2. Настроить идентичность компонента

1. Задайте уникальный `name` и понятный `title` в `docs/antora.yml`;
2. Заполните xref:architecture/overview.adoc[] под конкретный продукт;
3. Удалите неиспользуемые страницы и пункты навигации;
4. Адаптируйте `globs` локальных правил Cursor;
5. Удалите нерелевантные примеры правил и документов.

=== 3. Зарегистрировать компонент в центральном playbook

В центральном репозитории добавьте источник:

[source,yaml]
----
content:
  sources:
    - url: https://example.gitlab.com/group/my-component.git
      branches: main
      start_path: docs
----

Проверьте, что `name` компонента не конфликтует с уже подключёнными источниками.

=== 4. Проверить сборку

В центральном репозитории выполните:

[source,powershell]
----
docker compose build antora
docker compose run --rm antora
----

Результат сборки должен появиться в `build/site`.
Для просмотра через локальный web-сервер:

[source,powershell]
----
docker compose up preview
----

После запуска откройте http://localhost:8080 .

Если в playbook задано `runtime.log.failure_level: none`, сборка может завершиться без падения при ошибках контента внешних компонентов.
Поэтому логи нужно просматривать вручную.

=== 5. Опубликовать

На текущем этапе публикация и CI/CD остаются ответственностью центрального репозитория и не добавляются в компонент.

== Чеклист перед merge request

* `docs/antora.yml` содержит уникальный `name`, осмысленные `title`, `version` и `nav`;
* все страницы из `nav.adoc` существуют;
* нет битых `xref:` и `include::`;
* `index.adoc` и `overview.adoc` заполнены под конкретный проект;
* `README.adoc` описывает репозиторий для GitLab и не дублирует весь сайт;
* компонент зарегистрирован в центральном playbook через `start_path: docs`;
* сборка в центральном репозитории прошла, новый компонент виден в UI сайта.

== Ограничения

* локальная сборка Antora в репозитории компонента не добавляется;
* CI-проверка ссылок и include в компоненте не добавляется;
* GitLab-рендер `README.adoc` не заменяет Antora-сайт;
* смена `name` в `antora.yml` требует согласования с владельцем центрального playbook.
