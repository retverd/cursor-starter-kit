= ADR-001: Skill для формирования ADR вместо правила Cursor
:navtitle: ADR-001 Skill для ADR
:description: Решение использовать Cursor Skill для процесса написания ADR, а не правило Cursor

* Дата: 2026-07-29
* Статус: Принято
* Владельцы: maintainers шаблона правил Cursor

== Контекст

В шаблоне уже есть xref:templates/adr-template.adoc[шаблон ADR] и журнал xref:architecture/decisions.adoc[].
Операционные инструкции агента historically живут в `.cursor/rules/`, включая процессные правила по запросу (например, `91-code-review.mdc`).

Формирование ADR — редкий, многошаговый процесс: собрать контекст и альтернативы, заполнить шаблон, связать решение с `decisions.adoc` и навигацией, проверить границы с архитектурой правил.
Такой процесс плохо ложится на модель правил Cursor:

* `alwaysApply` или широкий `globs` постоянно занимают контекстное окно инструкциями, нужными только при написании ADR;
* процессное правило диапазона `90`–`99` формально подходит, но смешивает «устойчивые ограничения поведения» с «плейбуком разовой процедуры»;
* подробный процесс ADR в правилах дублирует шаблон и журнал решений и размывает принцип «правила — для действий, документация — для объяснения».

В Cursor появились Skills (файлы `SKILL.md`): агент подключает их по релевантности `description`, а не на каждый чат.
Skills рассчитаны на специализированные workflow и могут ссылаться на шаблоны и вспомогательные материалы без постоянного шума в контексте.

== Решение

Для **формирования и обновления ADR** использовать **Cursor Skill**, а не отдельное правило Cursor.

Границы решения:

* источник структуры ADR остаётся в документации: xref:templates/adr-template.adoc[] и страницы в `docs/modules/ROOT/pages/architecture/`;
* skill хранит операционный плейбук агента: когда писать ADR, какие файлы трогать, как именовать, как обновлять журнал и `nav.adoc`, какие проверки выполнить перед завершением;
* skill подключается только при запросах вроде «подготовь ADR», «зафиксируй архитектурное решение», «обнови ADR»;
* в `.cursor/rules/` **не** добавлять правило вида `9x-adr*.mdc` с полным процессом написания ADR;
* глобальные и ограниченные правила по-прежнему задают инварианты (язык текстов, минимальность изменений, Antora-контракт, верификация результата) и применяются поверх skill.

Рекомендуемое размещение skill в репозитории компонента:

[source,text]
----
.cursor/skills/adr-authoring/SKILL.md
----

== Рассмотренные альтернативы

=== Процессное правило Cursor (`92-adr.mdc` и аналоги)

Отклонено как основной носитель процесса.
Плюс: уже знакомый паттерн (`91-code-review.mdc`).
Минус: процессные правила конкурируют с Skills за «редкие workflow»; длинный плейбук ADR раздувает каталог правил и хуже отделяет «как писать ADR» от «как агент ведёт себя всегда».

=== Инструкции ADR внутри `04-docs-concepts.mdc` или `01-rules-generation.mdc`

Отклонено.
Эти правила отвечают за смысл документации и развитие правил, а не за сценарий фиксации архитектурного решения.
Добавление ADR-плейбука нарушит одну ответственность на файл.

=== Только шаблон и журнал без skill и без правила

Отклонено как недостаточное для агента.
Без явного workflow агент чаще пропускает обновление `nav.adoc`, статус/владельцев, связь с `decisions.adoc` или смешивает ADR с обычной страницей документации.

=== Вынести все процессные правила (включая ревью) в Skills одним шагом

Отложено.
Это отдельное решение о миграции операционной модели.
Текущий ADR фиксирует только границу для **формирования ADR**.

== Последствия

Плюсы:

* контекст чата не засоряется процедурой ADR, пока она не нужна;
* процесс написания ADR можно сделать подробнее, чем уместно в коротком `.mdc`;
* чётче разделяются слои: правила = ограничения и инварианты, skill = сценарий задачи, docs = шаблон и зафиксированные решения;
* skill проще переносить между проектами, унаследованными из шаблона.

Минусы и ограничения:

* появляется ещё один тип артефакта (`.cursor/skills/`), который нужно описывать в bootstrap и сопровождении;
* активация skill зависит от качества `description` и от того, что агент распознал задачу как ADR;
* если в окружении Skills недоступны, fallback — ручное следование шаблону и этому ADR, без автоматического плейбука;
* решение не отменяет необходимость обновлять документацию при изменении смысла архитектурных выборов.

== Замечания по миграции

1. Добавить skill `.cursor/skills/adr-authoring/SKILL.md` с кратким `description` и шагами процесса; внутри ссылаться на xref:templates/adr-template.adoc[] и xref:architecture/decisions.adoc[], не копируя их целиком.
2. При создании ADR из skill: новый файл в `docs/modules/ROOT/pages/architecture/`, запись в xref:architecture/decisions.adoc[], пункт в `docs/modules/ROOT/nav.adoc`.
3. Не создавать правило Cursor с полным процессом ADR; при конфликте «правило vs skill» для этой задачи приоритет у skill и документации.
4. Кратко упомянуть слой Skills в xref:architecture/rules.adoc[] и в bootstrap-процессах отдельным изменением, когда skill реально появится в репозитории.
5. Вопрос миграции `91-code-review.mdc` и других процессных правил в Skills вынести в отдельный ADR или предложение изменения правила.
