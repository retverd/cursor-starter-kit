= План миграции с GitHub на GitLab: ревью и рекомендации

== Исходный план

[cols="1,2,6",options="header"]
|===
| № | Роль | Задача

| 1 | DevOps | Ежедневный бэкап volume GitLab в S3, 02:00 MSK, хранить 2 версии.
| 2 | Dev | Проверить уведомления по почте из GitLab.
| 3 | Dev | Составить полный список репозиториев для переноса.
| 4 | Dev | Закрыть все Merge Requests на GitHub.
| 5 | Dev | Удалить неактуальные ветки на GitHub.
| 6 | Dev | Склонировать репозитории из GitHub в GitLab средствами GitLab.
| 7 | Dev | Проверить доступы через добавление origin.
| 8 | Dev | Скорректировать конфигурации TG-уведомлений для GitLab.
| 9 | Dev | Заархивировать проекты на GitHub.
| 10 | Dev | Через 3 месяца удалить архивированные проекты на GitHub.
|===

== Замечания к существующим пунктам

=== Пункт 1 — бэкап

Две версии бэкапа — это минимум. При ежедневном цикле это покрывает всего двое суток, чего недостаточно для обнаружения ошибок, которые проявляются позже (повреждение данных, случайное удаление репозитория). *Рекомендация:* увеличить глубину хранения хотя бы до 7 последних версий (неделя) или использовать схему ротации (7 ежедневных + 4 еженедельных). Также стоит добавить задачу на периодическую проверку восстановления из бэкапа (restore-тест), иначе бэкап может оказаться нерабочим.

=== Пункт 3 — список репозиториев

Список должен включать не только имена, но и: наличие CI/CD конфигураций (GitHub Actions), secrets/variables, webhooks, интеграции (Telegram-боты, deploy keys), LFS-объекты, wiki, GitHub Pages. Всё, что не переносится автоматически средствами импорта GitLab, нужно задокументировать заранее.

=== Пункт 4 — терминология

На GitHub используются Pull Requests, не Merge Requests. Важнее: помимо закрытия PR стоит убедиться, что ценные обсуждения и решения из PR задокументированы, потому что после архивации/удаления GitHub-репозиториев история обсуждений будет потеряна.

=== Пункт 6 — импорт

Встроенный импорт GitLab переносит коммиты, ветки и теги, но *не переносит*: Issues с комментариями (переносит частично), webhooks, secrets/variables CI, конфигурации защиты веток (branch protection rules), deploy keys, GitHub Actions (требуют ручной миграции в `.gitlab-ci.yml`). Это нужно учесть и запланировать отдельными задачами.

=== Пункт 8 — TG-уведомления

Файлы вида `tg_notify_on_pullrequest.yml` — это конфигурации для GitHub Actions. В GitLab аналог реализуется через `.gitlab-ci.yml` с вызовом Telegram Bot API, либо через встроенные интеграции GitLab (Settings → Integrations → Telegram). Пункт сформулирован неопределённо («если это возможно»). *Рекомендация:* явно выбрать способ реализации и назначить ответственного.

=== Пункт 10 — удаление

Три месяца — разумный срок. Но перед удалением стоит сделать финальный полный экспорт (GitHub Archive / `gh repo clone --mirror`) и сохранить его в том же S3 как страховку.

=== До миграции

| 0.6 | Dev | Мигрировать GitHub Actions → `.gitlab-ci.yml` для всех проектов, где есть CI.

== Рекомендация по порядку

Текущий порядок в целом логичен, но есть нюансы:

. Пункт 2 (проверка почты) лучше выполнить *до* начала импорта, параллельно с пунктом 1 — это независимая задача и блокер для оповещений.
. Пункты 0.2–0.6 (подготовка GitLab) должны идти *перед* пунктом 6 (импорт).
. Пункт 8 (TG-уведомления) зависит от пункта 0.6 (миграция CI), поэтому его стоит планировать после.

== Риски

* *Потеря истории обсуждений* — GitHub Issues/PR comments не переносятся полностью. Рассмотреть экспорт через GitHub API до архивации.
* *Простой CI* — между архивацией GitHub и полной настройкой GitLab CI будет окно без автоматизации. Минимизировать через параллельную подготовку.
* *Глубина бэкапа* — 2 версии недостаточно для обнаружения отложенных проблем.
* *Внешние зависимости* — сторонние сервисы, ссылающиеся на GitHub URLs (документация, пакетные реестры, деплой-скрипты), перестанут работать.
